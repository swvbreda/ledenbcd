# Projecten & taken rules

Applies to /projecten UI, internal_projects/internal_tasks DB code, planner/topical/taskNotifications server functions.

- Internal 'Projecten & taken' (internal_projects/internal_tasks) is admin-only via has_role(...,'admin') RLS plus a trigger that only allows admin accounts as owner/assignee; board or member status must never grant access, and rows are archived/completed rather than deleted.
- Planner sync runs only in admin-checked server functions against one fixed target plan, one BCD project per Planner bucket (unique plan+bucket), reading tasks via the bucket endpoint with explicitly fetched details; POST is retried only on 429, uncertain creates are never auto-recreated without an admin decision, sync hashes are only stored for writes that actually landed, lock token + heartbeat + hard deadline bound each run, and nothing is ever deleted in Planner — prevents duplicates, cross-project imports and silent data loss.
- Topical-actions (internal_tasks.source_system='topical', server-owned source_ref): the task-list 'Afronden' button and editor never call Microsoft — Topical rows complete in one click via the audited RPC `topical_complete_local_only`, others via a plain update (`completeTaskLocally`); external completion lives only in the Topical tab. They complete either via the admin-only `topicalComplete` server function or the explicit audited admin RPC `topical_complete_local_only` (never fakes remote timestamps; reopening clears its audit). Full completion: original Microsoft To Do task completed + existing Planner task 100% via If-Match, local 'afgerond' allowed by trigger only after both are recorded in `topical_task_links`; generic Planner sync skips Topical tasks so imports are never duplicated and partial failures can't show false success.
- Task-assignment notifications originate only from the DB trigger on internal_tasks.assignee_id (one task_notifications row per transition, admin recipients, read-only to clients except the mark-read RPC); push delivery runs in the admin-only dispatchTaskPushes server fn with claim/attempt limits, so clients can never choose recipients and push failure never blocks saving.
- Project workspace (/projecten?project=<id>) extends internal_projects/internal_tasks with participants, append-only messages (incl. 'bronupdate' requiring source date/subject/mailbox/ref/last action/next step), checkpoints and trigger-written internal_project_events; author/actor/timestamps are forced by SECURITY DEFINER triggers (service-role inserts become 'bronimport', missing historical actors show 'Niet geregistreerd'), and claiming uses the atomic RPC `claim_internal_task` (only unassigned open tasks, only for auth.uid()) — so clients can never forge audit or steal tasks.
