# Project architecture decisions

- Member contact removal is a server-authorized durable saga (`contact_removal_prepare` → Auth ban/soft-delete → `contact_removal_finish`); DB guards block direct destructive contact saves, pinned UUID revocations deny REST/RPC immediately via PostgREST pre-request, and soft deletion retains historical actor foreign keys. Never replace it with browser-only deletion or hard Auth deletion.

- Use route-level `head()` and `src/lib/socialHead.ts` for social previews, keeping private route images mapped to the public login capture; this prevents disclosure while enabling unique initial-HTML metadata.
- Member passwordless access uses Supabase Auth OTP and an independent server activation switch; this prevents the preview UI alone from enabling live mail before RLS and Auth templates are ready.
- Component render tests live in src/components/**/__tests__/*.render.tsx and run via `bunx vitest run -c vitest.components.config.ts`; the app Vite config loads React twice under vitest.
- Admin password reset presentation lives in a dedicated form with local errors and isolated save state; security policy and authorization remain server-owned.
- Canonical source for purchase costs in budget/dossiers is `informer_ledger_entries` (via `ledger_entries_v`); `pull_creditors` never creates `budget_expenses` or picks a default line item, so imports cannot be miscategorised or counted twice.
- Declaration post/dossier lives on `internal_declarations.budget_line_item_id`/`dossier` (admin-only via trigger); for declarations with an Informer document it is mirrored into `ledger_entry_overrides` without overwriting an existing different assignment, so budget and dossiers read one assignment.
- Declaration default budget post is set server-side by trigger `zz_declaration_default_post` (type+year exact name match, only when empty, NULL when ambiguous or year mismatch) and mirrored once into `ledger_entry_overrides` on first Informer link; UI defaults alone could be bypassed and manual admin choices must never be overwritten.
- Declaration post/dossier allocation goes through the admin-only RPC `admin_allocate_declaration` (role, year, version check, provenance, snapshots, one transaction); client-side checks are not authorization, and only overrides with known internal notes plus no creator and a repair snapshot count as automatic.
- New approved declarations go to Informer as receipts (POST /receipts, DECL token in description); `internal_declarations.informer_doc_type` (server-owned) types every external id and all ledger/override/payment joins use (doc_type, informer_id), because Informer ids are not unique across namespaces.
- User rights load through the single-flight, generation-guarded controller in `src/lib/accessController.ts`; overlapping auth events must not race refreshes or let stale results/timeouts overwrite verified rights.
- Dashboard representation figures (totals, share, gemeenten, G4, experiment) for every role come only from public-stats via summarizeRepresentation; local member counts are incomplete and fallbacks must never be shown as fact.
- Ordinary members get core stats from the member directory plus aggregate-only RPCs (e.g. get_member_bank_aggregate); register/UBO/survey hooks stay admin/board-only.
- Lead visibility is denied at restrictive SELECT RLS and shared member/query boundaries; lead conversion caches are user-scoped and privileged-only, and member totals count canonical member rows without reconstructing converted leads.
- Het Strategiebureau eligibility check uses one-time PKCE codes (hashed, 60s, service-only tables without policies, exact audience allowlist in `src/lib/adviesEligibility.ts`) and returns only `{eligible}`; the bureau must never receive BCD credentials, tokens or member data.

- Subdirectories may have their own `AGENTS.md` (e.g. `src/components/projecten/`, `src/lib/` for WhatsApp/Mijn vragen); read it before changing files there or related internal-projects DB/server code.
- Internal 'Projecten & taken' is admin-only (has_role 'admin' RLS) except the narrow member read RPC described there; rules for tasks, Planner, Topical, notifications and project workspace live in `src/components/projecten/AGENTS.md`.
- The app MCP server (`src/lib/mcp/`, mounted at `/mcp`) is OAuth-only and read-only: every tool calls `requireAdmin` (admin row in user_roles under the caller's RLS) through a caller-token client, uses select-only whitelisted columns/projections with bounded pagination, and never uses service_role, generic SQL, finance/bank/UBO/private-contact data or project documents/dossiers/messages — keeps external assistants inside existing admin rights.
- Municipality "Beleid en documenten" reads only public source records from the Beleidsmonitor via `src/lib/bcdDocumenten*.ts` (server fn with requireSupabaseAuth + admin/board/`support_my_member_id`, DB rate limit `bcd_documenten_rate_hit`, fixed allowlisted https origin, derived HMAC key in header, strict response allowlist where incompatible shapes are errors); never via member/dossier sync, and externs keep their own legacy search in `src/components/extern/`.

- Outlook deadline scheduling uses the existing internal-secret POST contract and a private default-disarmed queue wake/drain cron; manual and scheduled callers share the same worker and original SQL claim, preventing duplicate lifecycle logic or user-supplied actors.
- Declaration submit pushes come only from trigger `zz_declaration_submit_notify` (one `declaration_notifications` row per submission event + every authorized fixed approver incl. the submitter, unique event_key, recipients from service-only `declaration_push_recipients()` re-checked with `is_declaration_approver`, never blocks saving); delivery uses only the service-only lease RPCs `declaration_push_claim`/`declaration_push_finish` (lock_token, expired lease → `unknown`, never auto-resent; only proven-rejected `failed` gets bounded backoff retry) from one shared worker in `src/lib/declarationPush*.ts`, called by `dispatchDeclarationPushes` (submitter/admin) and the internal-secret route `/api/public/declaration-push-dispatch`; the wake/tick + cron job are a separate manual activation (`supabase/activation/declaration_push_scheduler.sql`) behind `enabled` and `scheduler_armed` (both default false, no backfill) — so clients never choose recipients, no admin broadcast, no exactly-once claim.
