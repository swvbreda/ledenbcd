# Project architecture decisions

- Use route-level `head()` and `src/lib/socialHead.ts` for social previews, keeping private route images mapped to the public login capture; this prevents disclosure while enabling unique initial-HTML metadata.
- Member passwordless access uses Supabase Auth OTP and an independent server activation switch; this prevents the preview UI alone from enabling live mail before RLS and Auth templates are ready.
- Component render tests live in src/components/**/__tests__/*.render.tsx and run via `bunx vitest run -c vitest.components.config.ts`; the app Vite config loads React twice under vitest.
- Canonical source for purchase costs in budget/dossiers is `informer_ledger_entries` (via `ledger_entries_v`); `pull_creditors` never creates `budget_expenses` or picks a default line item, so imports cannot be miscategorised or counted twice.
- Declaration post/dossier lives on `internal_declarations.budget_line_item_id`/`dossier` (admin-only via trigger); for declarations with an Informer document it is mirrored into `ledger_entry_overrides` without overwriting an existing different assignment, so budget and dossiers read one assignment.
- Declaration default budget post is set server-side by trigger `zz_declaration_default_post` (type+year exact name match, only when empty, NULL when ambiguous or year mismatch) and mirrored once into `ledger_entry_overrides` on first Informer link; UI defaults alone could be bypassed and manual admin choices must never be overwritten.
- Declaration post/dossier allocation goes through the admin-only RPC `admin_allocate_declaration` (role, year, version check, provenance, snapshots, one transaction); client-side checks are not authorization, and only overrides with known internal notes plus no creator and a repair snapshot count as automatic.
- New approved declarations go to Informer as receipts (POST /receipts, DECL token in description); `internal_declarations.informer_doc_type` (server-owned) types every external id and all ledger/override/payment joins use (doc_type, informer_id), because Informer ids are not unique across namespaces.
- User rights load through the single-flight, generation-guarded controller in `src/lib/accessController.ts`; overlapping auth events must not race refreshes or let stale results/timeouts overwrite verified rights.
- Internal 'Projecten & taken' (internal_projects/internal_tasks) is admin-only via has_role(...,'admin') RLS plus a trigger that only allows admin accounts as owner/assignee; board or member status must never grant access, and rows are archived/completed rather than deleted.
- Dashboard representation figures (totals, share, gemeenten, G4, experiment) for every role come only from public-stats via summarizeRepresentation; local member counts are incomplete and fallbacks must never be shown as fact.
- Ordinary members get core stats from the member directory plus aggregate-only RPCs (e.g. get_member_bank_aggregate); register/UBO/survey hooks stay admin/board-only.
- Planner sync runs only in admin-checked server functions against one fixed target plan, one BCD project per Planner bucket (unique plan+bucket), reading tasks via the bucket endpoint with explicitly fetched details; POST is retried only on 429, uncertain creates are never auto-recreated without an admin decision, sync hashes are only stored for writes that actually landed, lock token + heartbeat + hard deadline bound each run, and nothing is ever deleted in Planner — prevents duplicates, cross-project imports and silent data loss.
- Topical-actions (internal_tasks.source_system='topical', server-owned source_ref) complete either via the admin-only `topicalComplete` server function or the explicit audited admin RPC `topical_complete_local_only` (never fakes remote timestamps; reopening clears its audit). Full completion: original Microsoft To Do task completed + existing Planner task 100% via If-Match, local 'afgerond' allowed by trigger only after both are recorded in `topical_task_links`; generic Planner sync skips Topical tasks so imports are never duplicated and partial failures can't show false success.
- Task-assignment notifications originate only from the DB trigger on internal_tasks.assignee_id (one task_notifications row per transition, admin recipients, read-only to clients except the mark-read RPC); push delivery runs in the admin-only dispatchTaskPushes server fn with claim/attempt limits, so clients can never choose recipients and push failure never blocks saving.
